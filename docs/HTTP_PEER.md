# Два компьютера: data с начала и с конца, безопасный импорт

Патч для `cb047173d66f60404aa2b757d6a96ea45a0b3021`.
Дополняет существующий загрузчик, не сбрасывая work и не меняя выбранную когорту.
Запуск CLI: Linux и Python 3.11, как у основного HTTP-загрузчика.
Совместим с отдельным патчем потокового выбора когорты после prefix.
Зависимости прежние: `requirements-http.txt`; обе машины должны использовать
одинаковые версии DuckDB/PyArrow. Код фильтрации общий для обоих загрузчиков.

**Обратная загрузка выполняет этап DATA.** Завершённый prefix и готовая когорта
берутся из существующей сессии. Ещё раз скачивать первый час на ноутбуке не нужно.

## Схема

- Рабочий ПК продолжает обычный `tools/download_google2019.py download` с начала.
- Ноутбук получает небольшой seed, а не всю рабочую БД. В seed есть sources,
  выбранные ID/rank, смысловые настройки и снимок уже завершённых data-шардов.
- Ноутбук обходит оставшийся список в обратном порядке. Каждый шард фильтруется
  тем же SQL и сохраняется отдельной парой `pieces/ID.parquet` + `pieces/ID.json`.
- Утром эти фрагменты импортируются в исходную `stage.duckdb`. Общая история
  из старого архива не копируется: в результатах ноутбука её нет.
- Ключ завершения — прежний `(phase='data', source_name)`. Если основной ПК уже
  обработал этот источник, фрагмент целиком пропускается. DISTINCT по строкам нет:
  настоящие повторяющиеся события не удаляются.
- Вставка строк и запись done происходят одной транзакцией. После успешного COMMIT
  повторный импорт не вставляет строки ещё раз, в том числе после аварии до checkpoint.
- Итоговые 15 GB формирует обычный загрузчик на основном ПК после покрытия всех
  источников. Каталог ноутбука является переносимым прогрессом, не готовым датасетом.

Не нужно угадывать середину диапазона: пересечения безопасно пропускаются.
При одинаковых сетях возможен выигрыш около двух раз, но он зависит от скоростей,
пересечений и времени передачи/импорта результатов.

## 1. Подготовить небольшой seed

На рабочем ПК остановить загрузчик Ctrl+C и дождаться его завершения. Применить
патч и выполнить из корня репозитория:

```sh
.venv-http/bin/python tools/google2019_peer.py seed \
  --work work/google2019-http \
  --output peer-seed
```

Можно указать распакованную **старую рабочую копию** work из имеющегося архива,
если в ней уже полностью завершён prefix и есть candidates. Пути внутри старого
config.json менять для создания seed не требуется: читается фактический `--work`.
Не допускается другой временной диапазон, режим столбцов, когорта или поколения
источников. Отставание снимка по data допустимо и даст только лишние пересечения.
При подготовке из отдельного архива/его отдельной распакованной копии основной
загрузчик может продолжать работать. Пауза нужна, если seed читается из его
активной work, и позднее для самого merge.

Если есть только архив, поддерживаются tar/tar.gz/zip:

```sh
.venv-http/bin/python tools/google2019_peer.py seed \
  --archive /path/to/work-backup.tar.gz \
  --output peer-seed \
  --disk-gb 100 --reserve-gb 5
```

Из архива временно извлекаются только stage.duckdb/WAL и два JSON. Полная структура
work не распаковывается. До извлечения проверяются размеры архива + временной БД
и свободное место. Если это не укладывается в 30 GB ноутбука, готовьте seed на
рабочем ПК. Временная извлечённая БД после создания seed удаляется. Исходный архив
не удаляется и не изменяется. Архив должен быть сделан после остановки writer;
согласованность архива, снятого посередине записи БД, гарантировать нельзя.

Передать на ноутбук только папку `peer-seed` и код проекта с этим патчем.
Затем на рабочем ПК снова запустить свою **прежнюю команду download** с теми же
параметрами и каталогами. Он продолжит работу независимо от ноутбука.

## 2. На ноутбуке скачать data с конца, с пределом 30 GB

```sh
uv venv --python 3.11 .venv-http
uv pip install --python .venv-http/bin/python -r requirements-http.txt
screen -S google2019-peer
.venv-http/bin/python tools/google2019_peer.py download \
  --seed /path/to/peer-seed \
  --root /path/to/peer-run \
  --order reverse \
  --disk-gb 30
```

Для отсоединения от screen: Ctrl+A, затем D. Для остановки: Ctrl+C.
Для продолжения повторить эту же команду. `--root` сначала должен быть пустым,
он не является старым work. Не редактировать seed.json вручную.

`--disk-gb 30` — **30 000 000 000 байт на рабочий каталог peer-run**, включая
результаты, кэш, контрольные файлы и логи. Значение выше 30 этот режим не принимает.
Резерв — по умолчанию 1 GB; дополнительно заранее вычитаются худшие размеры сетевых
cache-файлов и контрольных файлов. Поэтому полезные фрагменты займут меньше 30 GB.
Здесь нет второй растущей DuckDB с сырыми таблицами, spill отключён: фильтрация идёт
ограниченными Arrow-порциями. Parquet-writer проверяет оставшийся бюджет **перед
записью каждого блока**, включая footer. Очередь и внешний RSS-супервизор сохранены.

Параметры памяти: `--memory-mib 512 --rss-mib 1536 --threads 2 --batch-rows 16384`.
Параметры сети: `--network-workers 2 --prefetch-shards 2`. Их можно уменьшать при
возобновлении. `--max-new-shards N` позволяет остановиться после N новых фрагментов.
`--order forward` также поддерживается, но для двух машин нужен reverse.

При достижении бюджета job приостанавливается (код 75), сохраняет готовые пары,
а недописанный фрагмент не становится checkpoint. `status.json` показывает причину.
Готовые фрагменты можно импортировать и после такого прерывания. Сбой/перезапуск
не требует заново скачивать уже сохранённые и проверенные фрагменты ноутбука.

Бюджет относится к job, а не к остальным пользовательским файлам на компьютере.
Не храните на ограниченном диске ноутбука одновременно старый большой work-архив,
распакованный work и новый peer-run: для peer нужен только маленький seed. Скрипт
также останавливается при исчерпании физического свободного места.

## 3. Перенести прогресс утром

Остановить ноутбук, дождаться завершения процесса. Перенести папку peer-run целиком
или только три контрольных файла и каталог pieces. Не копировать пишущуюся папку.

Для архива **пишите его сразу на USB/внешний диск**, а не рядом с заполненным
peer-run на ограниченном диске ноутбука:

```sh
tar -czf /media/USB/peer-results.tar.gz -C /path/to/peer-run \
  seed.json sources.json cohort.parquet pieces
```

Локальный полный каталог + его полный архив могут превысить 30 GB: автоматического
создания такого архива скрипт не выполняет. Можно передать сам каталог без архива.
Файлы seed — несколько MB, а pieces — отфильтрованные данные, не исходные шарды.

## 4. Импортировать в основную сессию

На рабочем ПК остановить обычный загрузчик и дождаться выхода. Импорт из архива:

```sh
.venv-http/bin/python tools/google2019_peer.py merge \
  --work work/google2019-http \
  --bundle /media/USB/peer-results.tar.gz \
  --disk-gb 100 --reserve-gb 5
```

В `--bundle` можно указать сам перенесённый каталог или zip. Архив целиком не
распаковывается: сначала проверяются seed и метаданные, затем импортируется по
одному фрагменту. Для tar.gz это два последовательных чтения, без квадратичных seek
по gzip. Для каждого фрагмента проверяются SHA-256, размер, схема и число строк.

Совместимость проверяется по когорте, порядку rank, смысловым настройкам, source
manifest с поколениями файлов, коду фильтрации и версиям DuckDB/PyArrow. Неверный
seed отклоняется до изменения таблиц. Контрольный пример: при основном диапазоне
0..11000 и вспомогательном 10501..13800 будут пропущены 500 пересечений, добавлены
2800 новых шардов. Повторный импорт пропустит все 3300.

Импорт защищён тем же work/run.lock и супервизором памяти/диска. Писать в основную
БД одновременно с обычным загрузчиком нельзя — команда откажется брать занятый lock.
При ошибке ранее подтверждённые фрагменты сохраняются; текущая незавершённая
транзакция откатывается. Повторить merge безопасно. WAL — часть checkpoint,
не удалять его вручную. Checkpoint выполняется периодически; COMMIT атомарен
для строк и done каждого отдельного источника.

После сообщения `{"imported": ..., "skipped": ...}` снова запустить **свою прежнюю
основную команду download**. Её существующая проверка done автоматически учтёт
импорт: полученные с конца источники больше не скачиваются. БД основной сессии
не заменяется и не объединяется через DISTINCT.

## Если нужна ещё одна ночь на ноутбуке

После успешного merge подготовить **новый seed** из основной work в новый каталог
и передать его на ноутбук. Повторить peer download с новым `--seed`, но прежним
`--root`. При одинаковой identity обновится только знание о завершённых источниках.
Фрагменты, уже подтверждённые новым seed как находящиеся на основном ПК, будут
удалены из peer-run, освободив место. Без нового seed удалять локальные checkpoint
ради следующей партии не нужно: иначе ноутбук может снова скачать тот же хвост.

Сначала убедитесь, что merge завершился и основная БД сохранена. Архив ноутбука
при merge не изменяется и не удаляется автоматически.

## Границы гарантий

Гарантируются на уровне алгоритма: отсутствие повторного импорта источника,
сохранение настоящих дубликатов внутри источника, проверка происхождения/целостности,
атомарность одной порции и восстановление по checkpoint. Никакого обещания защиты
от физической поломки диска или согласованности копии работающей БД нет.
Полный многосуточный прогон на пользовательских машинах не измерен.
