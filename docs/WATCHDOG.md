# Запустить команду под надзором

`tools/watchdog.sh` — самостоятельный Bash-скрипт для Linux. Его можно перенести
в другой проект. Python, зависимости vmforecast и активация virtualenv самому
watchdog не нужны. Зависимости запускаемой программы нужны ей как обычно.

## Подготовить Linux

- Использовать Bash >= 4.4, systemd >= 243 и обычную пользовательскую сессию.
- Установить screen и стандартные Linux-утилиты:

```sh
sudo apt install screen systemd util-linux coreutils
chmod +x tools/watchdog.sh
systemctl --user show-environment >/dev/null
```

Сам watchdog запускать **без sudo**. Если последняя команда не работает,
сначала войти в обычную Linux-сессию пользователя. Контейнер без systemd,
обычный WSL без systemd и chroot не подходят; скрипт не переключается молча
на ненадёжный shell-цикл.

Для сохранения надзора после выхода из аккаунта и запуска после перезагрузки:

```sh
loginctl enable-linger "$USER"
loginctl show-user "$USER" -p Linger
```

На некоторых дистрибутивах включение linger потребует участия администратора.
Watchdog сам не запускает sudo и не изменяет настройки аккаунта. Без linger
закрытие одного терминала не останавливает задачу, пока остаётся пользовательская
сессия; завершение последней сессии может остановить user manager и все его службы.

## Запустить задачу

Перед первым запуском остановить прежний ручной запуск той же программы.
Watchdog управляет только своими процессами и не присоединяет уже работающий PID.

Из корня проекта:

```sh
./tools/watchdog.sh --name peer-seed -- \
  .venv-http/bin/python tools/google2019_peer.py seed \
  --archive /путь/на/ноутбуке/work-backup.tar.gz \
  --output /путь/на/ноутбуке/peer-seed --disk-gb 30
```

Допускается сокращённая форма с автоматически вычисляемым именем:

```sh
./tools/watchdog.sh .venv-http/bin/python tools/google2019_peer.py seed \
  --archive /путь/на/ноутбуке/work-backup.tar.gz \
  --output /путь/на/ноутбуке/peer-seed --disk-gb 30
```

Имя, screen-сессию и команды управления скрипт напечатает. Рабочий каталог,
точные аргументы и окружение сохраняются при регистрации. Пустые аргументы,
пробелы, Unicode и переносы строк в аргументах не теряются. Значения не проходят
через `eval`. Перезапуск использует сохранённое окружение, даже если терминал закрыт.
Сессионные переменные screen/systemd и адрес старой DBus-сессии не восстанавливаются.

Команда должна работать на переднем плане. Не добавлять `&`, `nohup`, собственный
screen или режим daemonize. Для shell-операторов явно запускать shell:

```sh
./tools/watchdog.sh --name example -- bash -lc 'first-command && second-command'
```

Повтор той же команды из того же каталога находит ту же регистрацию и **ничего
повторно не запускает**. При `--name` другое содержимое команды, другой каталог
или другие опции ресурсов под тем же именем отклоняются. Для другой задачи выбрать
другое имя; для повторного запуска прежней использовать `restart`.

## Ограничить память программы

Необязательный пример с суммарным потолком **4 GiB для всех процессов задачи**:

```sh
./tools/watchdog.sh --name bounded-job --memory-max 4G -- /path/to/program argument
```

- `--memory-max` задаёт `MemoryMax` отдельной cgroup программы, включая screen,
  обёртку и всех дочерних процессов. Существующие ограничения родительских cgroup
  тоже действуют. Для новой конфигурации использовать новое имя, остановив старую.
- Нужны cgroup v2 и делегированный user manager контроллер `memory`.
  Если этого нет, запуск с указанным лимитом отклоняется до запуска программы.
- Без этой опции дополнительного потолка памяти у программы нет.
- Это потолок использования памяти cgroup, **не резерв RAM и не общий лимит RAM+swap**.
  При необходимости ограничить swap отдельно средствами администратора/systemd.
- Слишком маленький лимит будет давать повторные OOM каждые пять минут. Подбирать
  лимит по измеренному пику всей задачи; число `4G` здесь не обещание достаточности.

Проверить применённые параметры:

```sh
./tools/watchdog.sh status bounded-job
systemctl --user show vmwatch-bounded-job.service \
  -p MemoryMax -p MemoryCurrent -p OOMScoreAdjust -p ControlGroup
```

## Посмотреть и остановить задачу

```sh
./tools/watchdog.sh list
./tools/watchdog.sh status peer-seed
./tools/watchdog.sh attach peer-seed
```

В screen отсоединиться через **Ctrl+A, затем D**. Это оставляет задачу работающей.
`Ctrl+C` внутри screen завершает команду; неуспешное завершение watchdog попытается
повторить на следующей проверке. Для намеренной остановки использовать:

```sh
./tools/watchdog.sh stop peer-seed
./tools/watchdog.sh restart peer-seed
```

`stop` отключает таймер, снимает блокировку сна и останавливает всю cgroup задачи.
`restart` сначала останавливает старую cgroup, затем включает таймер и ставит один
новый запуск в очередь. Команды остановки могут ожидать до 30 секунд для завершения
процессов; затем systemd применяет принудительное завершение.

## Проверить поведение перезапуска

| Событие | Действие |
|---|---|
| Первый вызов | Поставить один запуск в очередь systemd и вернуть терминал |
| Повторный вызов той же команды | Показать существующее имя без нового запуска |
| Программа работает или служба запускается/останавливается | Не создавать ещё один экземпляр |
| Ошибка, exit 75, SIGKILL, OOM или исчезновение screen | Поставить одну попытку запуска на следующей проверке |
| Новая попытка тоже не удалась | Дождаться следующей проверки, не крутить быстрый цикл |
| Код завершения 0 | Завершить надзор и снять блокировку сна на следующей проверке |
| Ручной `stop` | Остановить надзор до явного `restart` |
| Недоступен user manager/DBus | Не считать это доказательством падения программы |

Проверка планируется через 300 секунд после активации таймера, затем через 300
секунд после окончания предыдущей проверки, с точностью планировщика около секунды.
При перегрузке системы она может задержаться. Запуск асинхронный: сообщение
`Registered` означает регистрацию и постановку в очередь, **не успешный запуск**.
Следом проверить `status` и журнал.

Для постоянной команды, которую нужно запускать даже после кода `0`:

```sh
./tools/watchdog.sh --name daemon --always -- /path/to/foreground-program
```

Для `seed` и конечных загрузок `--always` не нужен. Watchdog повторяет ровно ту же
команду. Восстановление по checkpoint, идемпотентность, причины ошибок и очистка
временных данных остаются ответственностью программы. Он не лечит постоянный
неверный аргумент или повреждённый checkpoint.

## Понять устройство и пределы защиты

Постоянного Python/Bash-наблюдателя со `sleep 300` нет. Используется уже работающий
**systemd user manager**, который хранит таймер и очередь запуска служб.
Раз в пять минут он создаёт короткую проверку. Она обращается к состоянию службы,
а для перезапуска отправляет `systemctl --user start --no-block`: тяжёлый процесс
порождает systemd в другой cgroup.

На задачу создаются четыре unit-файла:

| Unit | Назначение |
|---|---|
| `vmwatch-NAME.timer` | Хранить расписание; отдельного процесса не имеет |
| `vmwatch-NAME-check.service` | Выполнить короткую проверку, с `MemoryMax=64M`, когда доступен контроллер памяти |
| `vmwatch-NAME.service` | Запустить `systemd-inhibit … screen -D -m … команду` в отдельной cgroup |
| `vmwatch-NAME-inhibit.service` | Держать блокировку сна, включая ожидание повторного запуска; только inhibit + sleep |

У screen используется режим `-D -m`, который не создаёт фоновый сервер путём fork:
его жизненный цикл виден systemd. Собственный screenrc исключает пользовательский
режим zombie и ограничивает scrollback 1000 строками. Выход команды записывается
отдельно, поскольку код завершения сервера screen не равен коду команды.
`KillMode=control-group` и `OOMPolicy=kill` у задачи убирают оставшихся дочерних
процессов при остановке/OOM. Проверка и inhibitor находятся в других службах.

У программы `OOMScoreAdjust=500`, что повышает вероятность выбора её процессов
ядром при OOM. Отрицательный, привилегированный OOM-приоритет watchdog не запрашивает.
Если короткую проверку убьют, таймер сможет создать её заново. Блокировка сна
ожидающего watchdog восстанавливается на следующей проверке, если её службу убили.
Работающая программа дополнительно держит собственную блокировку.

**Абсолютной гарантии «никогда не убьют» без административной политики нет.**
При убийстве всего `user.slice`/`user@UID.service`, остановке user manager,
зависании ядра, выключении питания или принудительном suspend эта схема тоже
может прерваться. Обычный пользователь не может обеспечить себе иммунитет от
всех решений OOM-killer и systemd-oomd. Более сильная гарантия требует отдельной
системной службы и политики памяти/приоритета, которую устанавливает администратор.
Автоматически менять такую политику для всей машины скрипт не будет.

Блокировка `sleep:idle:handle-lid-switch` требует разрешения logind. Она удерживается до остановки
надзора, но не запрещает администратору принудительное действие и не изменяет
настройки окружения рабочего стола, которое может игнорировать inhibitors.
Отказ получения блокировки не скрывается: payload не запускается без собственного
inhibit, ошибка попадает в журнал, следующая попытка — через пять минут.

`handle-lid-switch` также блокирует автоматическую обработку закрытия крышки
самим logind: одного `sleep` недостаточно при настройке `LidSwitchIgnoreInhibited=yes`.
Проверить поведение своего окружения рабочего стола, прежде чем закрывать крышку
с работающим заданием; оставить ноутбуку достаточное охлаждение.

Если журнал службы сообщает `Access denied` / `Interactive authentication required`,
это может быть политикой logind для фоновых user-служб: разрешение из интерактивного
терминала не обязательно распространяется на них. Администратор может создать
`/etc/polkit-1/rules.d/49-vmwatch-inhibit.rules`, подставив точный логин из `id -un`:

```js
polkit.addRule(function(action, subject) {
    if (subject.user === "YOUR_LINUX_LOGIN" &&
        (action.id === "org.freedesktop.login1.inhibit-block-sleep" ||
         action.id === "org.freedesktop.login1.inhibit-block-idle" ||
         action.id === "org.freedesktop.login1.inhibit-handle-lid-switch")) {
        return polkit.Result.YES;
    }
});
```

Это разрешает конкретному аккаунту брать эти блокировки, включая фоновые процессы;
не даёт право выключать машину или обходить OOM. После изменения выполнить
`./tools/watchdog.sh restart NAME`. Для отмены удалить именно этот rule-файл.
Скрипт не устанавливает правило автоматически. См.
[политику logind](https://github.com/systemd/systemd/blob/main/src/login/org.freedesktop.login1.policy).

## Найти состояние и ошибки

- Состояние: `${XDG_STATE_HOME:-$HOME/.local/state}/vmforecast-watchdog/NAME/`.
- Units: `${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user/vmwatch-NAME*`.
- Файлы состояния приватны; снимок окружения может содержать секреты. Не добавлять
  эту директорию в Git и не публиковать её как диагностический архив.
- Сохраняются аргументы, окружение, рабочий каталог, копия runtime-скрипта, последний
  exit code и маркеры остановки/успеха. Репозиторий не используется для состояния.
- Счётчик собственных логов/истории не растёт: события службы идут в journald,
  который имеет системную политику хранения. Watchdog не меняет эту политику.
- Вывод самой команды виден в screen, пока сессия существует. После её завершения
  scrollback исчезает. Для постоянного вывода использовать логирование программы;
  watchdog не создаёт бесконечный `screenlog` на диске.

```sh
systemctl --user status vmwatch-peer-seed.service --no-pager
journalctl --user -u vmwatch-peer-seed.service \
  -u vmwatch-peer-seed-check.service -u vmwatch-peer-seed-inhibit.service -n 50
systemctl --user list-timers --all 'vmwatch-*'
systemd-inhibit --list
screen -ls
```

Для проверки на своём Linux зарегистрировать короткую тестовую команду:

```sh
./tools/watchdog.sh --name watchdog-smoke -- bash -c 'echo started; sleep 60; exit 75'
./tools/watchdog.sh attach watchdog-smoke
# Отсоединиться: Ctrl+A, D. Через минуту команда завершится.
# При проверке примерно через 5 минут появится ровно один новый запуск.
./tools/watchdog.sh status watchdog-smoke
./tools/watchdog.sh stop watchdog-smoke
```

Проверить синтаксис units и тесты исходников:

```sh
systemd-analyze --user verify "$HOME/.config/systemd/user/"vmwatch-watchdog-smoke*.service \
  "$HOME/.config/systemd/user/vmwatch-watchdog-smoke.timer"
bash -n tools/watchdog.sh
python -m pytest tests/test_watchdog.py -q
```
