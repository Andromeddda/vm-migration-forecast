# Ограниченная выгрузка Google Cluster 2019

Использовать только BigQuery Sandbox без биллинга, Free Trial, карты и подтверждения
по телефону. Квота — 1 ТиБ обработанных запросами данных в месяц. При исчерпании
квоты дождаться обновления; не подключать биллинг.

Перед выполнением SQL: `sh lab configure --project YOUR_PROJECT_ID`, затем
`sh lab auth`, затем `sh lab doctor`. Владелец публичного набора задаётся отдельно
через VMFORECAST_SOURCE_PROJECT (публичное значение дано в `.env.example`).
В ноутбуке project ID берётся из Settings; персональных идентификаторов в коде нет.

Первый notebook по умолчанию не обращается в сеть. Включение CONNECT_GOOGLE
разрешает metadata и dry run. Только EXECUTE_QUERIES=True разрешает реальные SQL.
CLI `sh lab run -- python -m vmforecast.google2019` по умолчанию делает dry run;
`--execute` включает выполнение. `--project` необязателен при настроенном .env.
Результат по умолчанию сохраняется в настроенный data-dir.

Параметры ExtractionConfig:

| Поле | Смысл |
|---|---|
| cell, t0, hours | Ячейка и временной интервал |
| prefix_hours, n_services | Детерминированный отбор когорты только по prefix |
| max_query_bytes | Максимум billed scan на запрос |
| total_budget_bytes | Консервативный суммарный scan-бюджет ledger |
| max_result_rows | Максимум строк до скачивания результата в pandas |

Dry run не расходует квоту обработки данных, но требует сети/доступа. Когорта и usage вычисляются одним SQL с одним обращением к instance_usage.
Предварительный план дополнительно оценивает events без фильтра по когорте;
точный targeted dry run events выполняется после получения выбранных ID.
Каждый реальный запрос проверяется повторно; maximum_bytes_billed передаётся в API.
Полный допустимый cap резервируется в query_ledger.json до запуска. Неизвестный
исход сохраняет резерв; успешный ответ заменяет его фактическим billed usage.
Запросы, превышающие бюджет, не выполняются. Не запускайте параллельные экстракторы
в один каталог: ledger не является распределённой транзакционной базой.

**Scan bytes не равны размеру скачивания.** Ограничение result rows проверяется
после выполнения SQL, до to_dataframe; квота обработки самого
запроса к этому моменту уже может быть израсходована. Текущий адаптер загружает результат в память целиком и затем пишет Parquet.
Он не гарантирует точную квоту байтов на диске и не реализует потоковую докачку.
Уменьшайте cohort/hours и проверяйте dry run; оставляйте запас RAM и диска.
3 GiB preflight — порог допуска deployment, а не гарантия размера результата.
Для больших объёмов нужен отдельный streaming/chunking адаптер с byte cap.

Повторный extraction сохраняет ledger, но может повторно выполнить запросы и
израсходовать квоту; это не resume готовых Parquet. При смене параметров используйте
новый output directory. Не удаляйте ledger, чтобы обойти лимит. Напротив,
`run_saved` для симуляций проверяет checksum и повторно использует завершённые run.

Usage и instance_events нужны для строгого контроля покрытия/lifecycle.
Metadata остальных таблиц сохраняется для проверки схемы; machine logs не
используются для калибровки overhead или задержки миграции. Расширение этих
экспериментов — отдельная научная задача, не эффект изменения deployment.

Публичный источник и условия: [Google Cluster Data 2019](https://github.com/google/cluster-data/blob/master/ClusterData2019.md).
Настройка Google Cloud и браузерные шаги находятся в корневом README.


## Проверить объединённый запрос в авторизованном окружении

1. Обновить ветку с изменениями и перезапустить kernel для загрузки нового кода.
2. Создать новый output-каталог, например `LAB_DATA_DIR/'google2019_combined_a_3h_10'`.
   Не удалять старые ledger. Их расходы и резервы не исчезают из квоты Google.
3. Создать `BoundedExtractor(client, CFG, DATA_DIR)` с нужной конфигурацией.
4. Оставить `EXECUTE_QUERIES=False` и выполнить:

```python
plan = extractor.plan()
display(plan)
```

План не выполняет реальные запросы, не скачивает данные и не резервирует бюджет.
Он возвращает обе оценки даже при превышении ограничений. `usage` включает
prefix-cohort и usage за весь интервал. `events_scan_upper_estimate` оценивает
чтение полей events без фильтра по когорте: консервативный ориентир, не точный
targeted scan. `total_scan_upper_estimate_bytes` суммирует эти две оценки;
это не размер Parquet и не остаток Sandbox allowance. Окончательное соблюдение
`maximum_bytes_billed` и остатка ledger проверяется отдельно перед каждым job.
При неизвестной оценке или превышении лимита выполнение не разрешается.

Источник instance_usage упоминается в объединённом SQL один раз. Покрытие prefix
и порядок FARM_FINGERPRINT с ID для разрешения совпадений сохранены. Отбор не
проверяет наличие будущих наблюдений; строгая проверка полного периода остаётся
в подготовке данных. В частности, исторический критерий SUM перекрытий prefix
сохранён, а не заменён новой проверкой качества интервалов.

После разрешённого выполнения создаются usage.parquet, выведенный из него
cohort.parquet (без отдельного BigQuery job) и targeted events.parquet. Ledger
содержит только два запроса: usage и events. Стратегия `combined_usage_v1`
записана в ledger и manifest. Старый непустой ledger другой стратегии отклоняется;
пустой ledger без расходов может быть использован. Автоматического resume нет.

Не увеличивать лимиты по умолчанию и не включать EXECUTE_QUERIES до проверки плана.
Объединение устраняет отдельный запрос cohort, но не обещает конкретного scan или
попадания в 192 GiB: таблица источника может оставаться непартиционированной.
При переходе к notebook 02 указать тот же новый каталог prepared. Возвращаемое
значение `extract()` остаётся `(usage, events)`; dry-run extract возвращает None.
`build_queries()` теперь возвращает usage, events и events_scan вместо cohort.

## Проверить локальную эквивалентность

```sh
sh lab run -- python -m pytest -q tests/test_combined_extraction.py tests/test_data_and_runs.py
```

Тесты выполняют production SQL на маленьких SQLite-таблицах с оконными функциями
и сравнивают с прежним двухэтапным алгоритмом. Адаптируются только имя таблицы,
поля struct и hash-примитив. Hash-заглушка проверяет знаковую сортировку и коллизии,
но не реализацию FARM_FINGERPRINT. Проверены разные границы интервалов, null в
prefix и после него, неполное будущее, большие ID, пустая когорта, фильтры alloc,
лимиты, ledger и ровно два реальных запроса с fake client. Это не тест выполнения
в BigQuery и не измерение экономии; авторизованный dry run остаётся обязательным.
