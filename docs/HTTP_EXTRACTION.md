# Google Cluster 2019: локальная HTTP-выгрузка без BigQuery

Скрипт: `tools/download_google2019.py`; реализация: `src/vmforecast/google2019_http.py`.
Работает на Linux, без OAuth, Google SDK, Colab, Jupyter и браузерных WebSocket.
HTTP-запросы к публичному хранилищу всё равно используют обычные сетевые соединения.
SQL выполняется только локально в DuckDB. Квота SQL BigQuery не расходуется.

## Установка и запуск на выходные

Из корня репозитория, Python 3.11:

```sh
uv venv --python 3.11 .venv-http
uv pip install --python .venv-http/bin/python -r requirements-http.txt
screen -S google2019
.venv-http/bin/python tools/download_google2019.py download \
  --output /home/USER/migration-data/google2019_http_a_30d \
  --work /home/USER/migration-scratch/google2019-http
```

Заменить `USER` и пути. Каталоги `--work` и `--output` должны быть раздельными,
не вложенными друг в друга. Рабочий каталог — на локальном диске, не на сетевом
монтировании. Лучше сначала сохранять результат локально и переносить готовый
каталог после завершения. Другие файлы на диске скрипт не удаляет.

Отсоединиться: Ctrl+A, затем D. Вернуться: `screen -r google2019`.
Лог ограничен ротацией: `WORK/download.log` и три предыдущих файла по 4 MiB.
Не включайте бесконечное внешнее логирование `screen`/`tee`, если оно не нужно.

Прервать можно Ctrl+C. Для продолжения запустить ту же команду. Транзакция
незавершённого шарда откатится; сам этот шард будет скачан повторно.
Успешно завершённые шарды повторно не скачиваются. Один work/output защищён
от конкурентного запуска файловыми блокировками.

## Ограничения по умолчанию

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `--days` | 30 | Общее окно истории от `t0` |
| `--t0` | 600000000 | Микросекунды относительно начала трейса |
| `--prefix-hours` | 1 | Начальный период для выбора когорты |
| `--max-objects` | 25000 | Верхняя граница числа отдельных `(collection_id, instance_index)` |
| `--target-gb` | 15 | Жёсткий предел готового каталога в десятичных GB |
| `--disk-gb` | 100 | Бюджет суммы output и work; защитная остановка раньше предела |
| `--stage-gb` | 65 | Защитный предел основного локального staging-файла |
| `--spill-gb` | 8 | Предел временных файлов сортировки DuckDB |
| `--reserve-gb` | 5 | Сколько свободного места оставлять на файловой системе |
| `--memory-mib` | 512 | Буферная память DuckDB, не общий RSS процесса |
| `--rss-mib` | 1536 | Порог RSS рабочего процесса, контролируемый супервизором |
| `--threads` | 2 | Число потоков DuckDB |
| `--batch-rows` | 16384 | Размер обрабатываемой Arrow-порции |
| `--columns` | research | Все исходные столбцы, включая вложенные |
| `--retry-hours` | 12 | Время повторов одного HTTP-запроса при временных ошибках |
| `--keep-stage` | выключен | Сохранить staging-БД после успешной проверки результата |

Запуск намеренно имеет низкий CPU-приоритет. Супервизор проверяет память и диск
каждые 0,5 секунды; при системной доступной памяти ниже 256 MiB работа приостанавливается.
Проверки — защитные пороги, а не резервирование RAM/диска ядром: другие приложения
могут одновременно расходовать ресурсы. Для ещё более тесной машины снизьте буфер
и размер порции при первом запуске, например `--memory-mib 256 --threads 1
--batch-rows 4096 --rss-mib 1024`. Желательно хотя бы 2–3 GB доступной RAM на старте.

При недостатке ресурсов/изменении источника скрипт останавливается с кодом 75,
сохраняя checkpoint, вместо пропуска данных или бесконечного заполнения диска.
Ошибки HTTP 429/5xx и временные сетевые сбои повторяются с задержками; 403/404
считаются проблемой источника и не превращаются в «конец списка».
Нельзя гарантировать завершение за выходные при любой скорости сети и любых сбоях.

Параметры запуска зафиксированы в `WORK/config.json`. Для изменения состава,
окна, числа объектов или целевого размера нужен отдельный новый work/output;
это защищает от смешивания наборов при resume. Лимиты RAM/рабочего диска,
число потоков, размер порции, сетевые повторы и `--keep-stage` можно менять
при возобновлении. После освобождения диска повтор прежней команды безопасен.

## Как строится набор

1. Получить список всех пяти таблиц cell a, зафиксировать имена, размеры и поколения
   исходных объектов. Дальнейшие HTTP Range адресуются к этим поколениям.
2. Пройти usage только по необходимым для начального часа столбцам. В локальной БД
   оставить интервалы, пересекающие этот час, отбрасывая alloc/double-counting и
   некорректные наблюдения. После полного прохода проверить покрытие без разрывов
   и наложений и выбрать до 25 000 инстансов в воспроизводимом MD5-порядке.
3. Вторым проходом собрать usage за все 30 дней и события выбранных инстансов,
   включая историю событий до начала окна. Сохранить события соответствующих
   collections, machine events и machine attributes. События хостов сохраняются
   по всей cell, так как эти таблицы малы.
4. Проверить непрерывность usage и консервативные требования жизненного цикла
   текущего бэктестера. Пропуски не заполняются; рестарты не склеиваются.
5. Экспортировать целые пары файлов usage/events каждого инстанса в порядке когорты,
   пока они помещаются в 15 GB. Большая пара, не помещающаяся в остаток,
   пропускается; меньшие последующие пары могут быть сохранены. Временное окно
   сохраняется общим для всего набора. Диагностика качества не используется для
   скрытого удаления «плохих» историй из исследовательской выгрузки.

Исходные архивы на диск не создаются. Временный sparse Parquet содержит только
полученные HTTP Range блоки одного источника и удаляется после его обработки.
В research-режиме требуются все столбцы: сетевой объём будет близок к полному
Parquet-экспорту usage cell a (~408 GiB), плюс первый проход и остальные таблицы.
В `--columns core` скачиваются только поля для бэктестов и отбора; трафик меньше,
но в результате не будет дополнительных usage-метрик и распределений.
Ни один режим не расходует SQL-квоту BigQuery.

Не обещаем ровно 15 GB: 30 дней, ограничение числа инстансов, имеющиеся измерения
и сжатие могут дать меньший набор. research сохраняет дополнительные реальные
метрики для подробного анализа. Для увеличения числа объектов можно задать больший
`--max-objects` при новом запуске, учитывая staging-бюджет. Заполнение до последнего
байта, дубликаты и искусственная генерация измерений не применяются.

## Результат и проверка

Готовность обозначается `manifest.json` со `status=complete`. До этого каталог
не является законченным датасетом. В нём:

| Файл/каталог | Содержание |
|---|---|
| `usage.parquet/ID_INDEX.parquet` | Все сохранённые интервалы этого инстанса, исходные поля и алиасы cpu/mem |
| `events.parquet/ID_INDEX.parquet` | История событий этого инстанса, исходные поля и алиасы cpu_request/mem_request |
| `cohort.parquet` | Сохранённые идентификаторы и порядок отбора |
| `candidate_cohort.parquet` | Вся prefix-когорта до ограничения байтами и признак retained |
| `quality.parquet` | Покрытие и lifecycle-валидность полного окна по каждому инстансу |
| `checksums.parquet` | SHA-256 каждой пары usage/events и её фактический размер |
| `machine_events.parquet` | События и capacity хостов |
| `machine_attributes.parquet` | Атрибуты хостов |
| `collection_events.parquet` | События выбранных collections |
| `manifest.json` | Настройки, исходные файлы/поколения, числа исходных строк, качество и размер |

`usage.parquet`/`events.parquet` здесь **каталоги Parquet dataset**, а не прежние
монолитные файлы BQ-экстрактора. Не загружайте все 15 GB через pandas одним вызовом.
Анализировать можно через DuckDB/Arrow с проекцией нужных полей и ограничением окна.
Числа исходных строк в manifest позволяют сверить экспорт с метаданными BQ без
платных запросов; одно совпадение размеров не доказывает идентичность содержимого.
Упаковка по размеру файлов полного периода тоже способна смещать состав набора;
исходные кандидаты сохранены отдельно, чтобы этот отбор был виден.

Пример просмотра небольшого отчёта:

```sh
.venv-http/bin/python - <<'PY'
import json
from pathlib import Path
p = Path('/home/USER/migration-data/google2019_http_a_30d')
m = json.loads((p/'manifest.json').read_text())
print({k:m[k] for k in ['status','instances','full_window_backtest_valid_instances','output_bytes']})
PY
```

## Сразу запустить бэктест на ограниченном срезе

Для подготовки нужен сам пакет проекта (Google extra не нужен):

```sh
uv pip install --python .venv-http/bin/python -e .
.venv-http/bin/python tools/download_google2019.py prepare \
  --dataset /home/USER/migration-data/google2019_http_a_30d \
  --destination /home/USER/migration-data/google2019_http_a_30d_backtest/prepared \
  --objects 64 --hours 168
```

Команда выбирает до 64 инстансов с полным покрытием и допустимым жизненным циклом
в первую неделю, повторно проверяет их через `prepare_usage` и создаёт существующий
формат `workload.npz`/`workload.json`/`quality.json`. Если непрерывных историй нет,
она объясняет причину: попробуйте меньше `--hours` или другое `--offset-hours`.
Срез для бэктеста пишите **вне исходного 15 GB каталога**.

Отбор по полному будущему окну помечается как exploratory complete-case и имеет
survivorship bias. Это пригодный полигон, но не безусловно репрезентативная когорта.
Capacity хостов в подготовленном workload синтетические, вычислены по начальному
часу; это не восстановленное реальное размещение Google. Исходные host events
сохранены отдельно для последующей работы.

В notebook 02 включить `USE_GOOGLE=True` и заменить загрузку workload на:

```python
workload = load_workload(Path('/home/USER/migration-data/google2019_http_a_30d_backtest/prepared'))
WARMUP = 12
```

В notebook 03 аналогично указать подготовленный каталог. Обработка всех объектов
сразу в существующих ноутбуках может требовать много RAM: запускайте несколько
ограниченных экспериментов. prepare ограничивает размер среза по оценке RAM.

## Очистка и перенос

После `COMPLETE` супервизор проверяет SHA-256 готовых файлов и **автоматически
удаляет свою staging-БД и временные файлы**. До завершения checkpoint сохраняется
для resume. Для сохранения БД после успешной выгрузки задайте `--keep-stage`.
Небольшие config/sources/log остаются в work; весь этот каталог затем можно убрать
вручную. Скрипт освобождает source/spill/export-group файлы в процессе.
Повтор исходной команды после завершения проверяет готовый набор без новой загрузки.
Для облачного хранилища переносить только готовый output, без work и prepared-срезов.

Проверить уже перенесённый датасет без work:

```sh
.venv-http/bin/python tools/download_google2019.py verify \
  --dataset /path/to/data/google2019_http_a_30d
```

## Проверено

Автоматические тесты используют настоящий локальный HTTP Range сервер и небольшие
Parquet-шарды: непрерывная история, разрыв после prefix, lifecycle-остановка,
повторный запуск, целочисленные ID, research/core, побайтовый бюджет пары, изменение
выходного файла, отказ сервера выполнять Range, нехватка диска, остановка по RSS,
standalone CLI и запуск настоящего бэктестера на подготовленном workload.
Полный месячный прогон и длительность на пользовательском ПК не проверены.
